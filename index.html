一次构建经过哪四步

以 OneStar 的命令行构建为例

没有 Gradle，四个工具按顺序打完一遍，出 APK。每一步都能单独跑、单独看输出，出错时知道是资源、字节码还是签名的问题。

  1. 01 aapt2

    编译并链接资源，生成带资源表的容器

  2. 02 javac

    编译 Java 源码，产出 class 文件

  3. 03 d8

    把 class 转成 dex，打进容器

  4. 04 apksigner

    签名并校验，产出可安装的 APK

JNI 那一层不在这条链上：它由 zig cc 单独编译成 .so，在 d8 之前放进同一次打包。好处是构建脚本只有百来行，坏处是所有约定都得自己记住——所以构建规范写进了文档，而不是留在脑子里。

做事方式

原生优先
界面用 Canvas 逐帧画，不套 WebView，不为了快而牺牲可控。
依赖克制
能自己写的一行，就不引入一个包。构建链的每一环都要说得清做了什么。
可复现
命令行能编译出同一种 APK，构建过程不依赖 IDE 的隐式魔法。
文档写实
README 里同时记限制、踩坑和已知问题，不只写亮点。
